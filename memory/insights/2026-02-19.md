# Insights — 2026-02-19

### 11:30 — Chrome extension: must remove+re-add when adding content_scripts

**Problem:** After adding `content_scripts` to an already-installed extension's manifest.json, clicking
the reload (⟳) button on `chrome://extensions` does NOT register the new content scripts. Chrome shows
"This extension has no additional site access" even though the manifest on disk has match patterns.

**Root cause:** Chrome registers content script match patterns during *installation*, not on every reload.
The reload button refreshes code but doesn't re-process structural manifest changes like new content_scripts.

**Fix:** Fully **Remove** the extension, then **Load unpacked** again. This forces Chrome to re-parse
the manifest from scratch and register the content scripts properly.

**How to verify:** After loading, click Details on the extension card. "Site access" should list the
matched domains (e.g., linkedin.com, indeed.com). If it says "no additional site access", the content
scripts weren't registered.

**Also applies to:** Adding new permissions, changing match patterns, adding new content script entries.
Basically any structural manifest change — remove and re-add to be safe.

### 09:00 — Competitive research: the real landscape

**Pain points users hate most (across Huntr, Teal, Simplify, Careerflow, Eztrackr):**
- Manual entry fatigue — ironic that tracking tools add friction to job search
- Job caps on free tiers (Huntr 100, Careerflow 10) feel hostile to people between jobs
- Feature bloat — Teal and Careerflow overwhelm users who just want tracking
- AI content (cover letters, resumes) described as "generic" requiring heavy editing
- Data loss / sync issues, especially cross-device (Eztrackr iOS, Careerflow bugs)
- Privacy violations — Simplify published user support requests with PII publicly
- Pricing feels predatory when users are unemployed ($40/mo Huntr, $29/mo Teal)

**What users genuinely love:**
- One-click save from job boards (Eztrackr's Chrome extension praised)
- Visual kanban with simple 4-status columns (not 12-column monsters)
- "Everything in one place" — unified dashboard reduces anxiety
- Follow-up reminders — surfacing the right info at the right time
- Free with no cap builds loyalty and trust
- Teal's inline LinkedIn job surfacing called "a feature I haven't seen anywhere else"

**The gap we're filling:**
- NO tool does true passive detection — every one requires a deliberate user action
- Simplicity-as-product is unoccupied — everyone's building career platforms, not trackers
- Email parsing (Gmail "application received") is wanted but no free tool does it
- Application analytics (velocity, response rate, source effectiveness) are paywalled everywhere
- Data export (CSV/JSON) builds trust — users fear vendor lock-in
- Daily application goals / streaks — treating job search as a habit is unaddressed

### 09:30 — Architecture decision: vanilla TS, no framework

Popup is ~150 lines of DOM manipulation. A framework would add bundle weight for zero benefit.
Using safe DOM construction (createElement + textContent) instead of innerHTML to prevent XSS.
esbuild bundles everything to IIFE — no module system needed in the extension runtime.

### 10:00 — LinkedIn detection: stable selectors

**Primary success signal:** `h2#post-apply-modal` — appears when "Application sent" confirmation shows.
Confirmed across 6 open-source automation tools (s00ar, Azoo92i, GodsScion, davidwarshawsky, NathanDuma).

**Reliable fallback for job data:** `document.title` — LinkedIn sets it to "[Title] at [Company] | LinkedIn".
Zero selector fragility, works even when class names change.

**Class stability:** LinkedIn's `artdeco-*` design system classes are relatively stable. `jobs-*` prefixed
classes have had minor renames across versions (e.g., `jobs-unified-top-card` → `job-details-jobs-unified-top-card`).
Strategy: try multiple selectors in priority order.

**No Shadow DOM.** Confirmed by all implementations — everything is directly queryable.

### 13:00 — chrome.storage.session.get() returns {} not undefined for missing keys

`chrome.storage.session.get('someKey')` returns `{}` when the key doesn't exist, NOT `undefined`.
Since `{}` is truthy in JS, `session.get(key) || local.get(key)` never falls through to local.
Fix: explicitly check `key in result` before using the session result.

This caused a cross-tab data handoff failure: main page wrote to chrome.storage.local, wizard tried
chrome.storage.session first, got `{}`, treated it as the answer, and never checked local.

### 10:00 — Indeed detection: the full picture (confirmed working)

**Architecture:** Two content script contexts running on different subdomains:
- **Main page** (`*.indeed.com`) — extracts job data from DOM, caches it via `chrome.runtime.sendMessage` to background service worker (in-memory variable)
- **Wizard** (`smartapply.indeed.com`, `m5.apply.indeed.com`) — watches for completion signals, retrieves cached job data from background via messaging

**Cross-tab data handoff — use background messaging, NOT chrome.storage:**
- `chrome.storage.session` is unreliable for cross-tab reads (returns `{}` for missing keys, which is truthy)
- The working approach: main page sends `CACHE_JOB_DATA` to background SW, wizard sends `GET_CACHED_JOB`
- Background holds data in a simple `let cachedJob` variable — no storage APIs needed
- Keep chrome.storage.local as a backup fallback only

**Apply button detection — delegate + text match:**
- Indeed's Apply button selectors change. Use event delegation on `document.body` with `capture: true`
- Match by selector first (`.ia-IndeedApplyButton`, `[data-testid="indeedApply-button"]`, etc.)
- Fall back to text matching: "apply now", "apply on", "submit application", etc.
- On click: cache current job data AND set a `pendingIndeedApp` flag

**Job data extraction — DOM first, document.title fallback:**
- `data-testid` attributes are most stable (`inlineHeader-companyName`, `jobsearch-JobInfoHeader-title`)
- Also try `.jobsearch-*` classes and `span.companyName` / `h2.jobTitle` for older layouts
- Last resort: parse `document.title` which follows pattern "Role - Company | Indeed.com"

**Job key (`jk`) is not always in the URL:**
- Indeed's split-view doesn't always put `?jk=` in the URL
- Also check `[data-jk]` attributes on job cards
- Generate a fallback key from `company-role` if no jk found — caching still works

**Completion signals in wizard:**
- `.ia-HasApplied-bodyTop`, `.ia-ThankYou`, `.ia-PostApply`, `[data-testid="ia-success"]`
- `.ia-BasePage-heading` containing "application submitted" / "you've applied" / "thank you for applying"
- URL containing "post-apply", "confirmation", or "submitted"

**Wizard also checks page text for job data:**
- `.ia-PostApply-header h1` for role, `.ia-PostApply-header .company` for company
- `document.title` pattern: "Apply for [Role] at [Company]"
- Body text regex: `applied to/for [role] at [company]`

**Polling is essential:** Indeed is an SPA. Job data loads asynchronously after navigation.
Poll `tryCacheCurrentJob()` every 3 seconds + on URL change + on DOM mutations.

**~40% of Indeed listings redirect to external ATS** (Workday, Greenhouse, etc.) — cannot detect
these from Indeed's domain. Will need separate detectors per ATS in Week 3.

### 14:15 — Debugging content scripts: version-tag your init messages

When iterating on content script code, add a version number to the init `console.warn`:
```
console.warn('[Logged] Indeed detector v0.3 initialized (main page)');
```
This immediately tells you whether the reload actually picked up your changes. Saved us from
debugging stale code multiple times. Also use `console.warn` instead of `console.log` so it
stands out in the console.
